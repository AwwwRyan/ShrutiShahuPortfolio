## Decisions log

Chronological. Each entry is a decision that's settled — don't revisit without new information.

1. **Stack:** Next.js (App Router) full-stack app, single deployable, hosted on Vercel.
2. **Database:** Postgres via Prisma ORM, provider is **Neon**, provisioned through the Vercel Storage integration (gets Neon's free tier + Vercel's env var integration).
3. **Auth:** NextAuth.js, credentials provider, single admin account (Shruti), no public sign-up. Admin provisioned via seed script.
4. **Password reset:** Email-based single-use link, 1-hour expiry, token hashed at rest, sent via Resend. Chosen over security questions / magic-link-only because it reuses infra already committed to (Resend + Prisma) and there's only one account to secure.
5. **File storage:** Vercel Blob for images and docs (cover images, gallery images, PDFs). Chosen for low traffic (<100 users/day) — no need for a managed server disk, generous free tier, zero-config with Next.js.
6. **Video hosting:** External (YouTube/Vimeo, unlisted), embedded via URL — NOT uploaded to Blob. Reasoning: sample videos run 10–33MB each; direct Blob hosting would mean real storage cost and no adaptive streaming. Blob storage stays scoped to images/docs only.
7. **Rich text editor:** Tiptap, for project descriptions and About Me.
8. **Contact form:** Working form (name/email/message) → Resend → email to Shruti. Not just static contact info.
9. **Categories are fully dynamic and multi-level** (self-referencing `parentId` on Category, unlimited depth). The four category names in the README (Writing, Editing, Marketing, Digital Journalism) are seed data only, not hardcoded. A category can hold both subcategories AND projects directly at the same time (folder-with-files-and-subfolders model) — projects are not restricted to leaf categories.
10. **Project fields beyond the original spec:** client/publication name, tags (freeform, separate from category), multiple `links[]` (each with label + url), featured flag, manual order, cover image, `gallery[]` (multi-image, for carousel-style pieces like the Digital News series), `videoUrl` (external embed for video projects).

## Technical learnings

- **Read tool cannot open `.docx`/`.xlsx` directly** ("binary file" error). Both formats are zip archives of XML under the hood — wrote a stdlib-only Python script (no pip installs needed) at the time to extract text: `word/document.xml` for docx (`<w:t>` runs), `xl/worksheets/sheet*.xml` + `xl/sharedStrings.xml` for xlsx. Reusable approach if more Office docs show up.
- **`python3` on this machine is a broken Windows Store alias.** Use the real interpreter directly: `/c/Users/Aryan/AppData/Local/Programs/Python/Python312/python` (from Git Bash). `python-docx` / `openpyxl` are NOT installed — stick to the stdlib zip/XML approach rather than assuming they're available.
- **Read tool handles PDFs and images natively** (renders pages/images for multimodal viewing) — no extraction script needed for those, unlike docx/xlsx.
- **Markdown lint hook is active on this repo** (PostToolUse on Write) — enforces blank lines around headings and lists (MD022/MD032) and table pipe alignment (MD060). Write markdown with blank lines around every heading/list and aligned table columns from the start to avoid a follow-up fix pass; for tables, generate the padding programmatically (e.g. a quick script) rather than hand-aligning pipes.
- **Next.js 16 (Turbopack) here is newer than training data — read its bundled docs before writing app code.** `create-next-app`/`next dev` auto-generate `AGENTS.md` (imported by `CLAUDE.md` via `@AGENTS.md`) warning that APIs/conventions/file structure may differ from what's expected, and pointing to `node_modules/next/dist/docs/` as the source of truth. Consult that before writing App Router routes, data fetching, or config in Stage 2+ rather than assuming pre-16 patterns still apply.
- **`npm install` can drop mid-download (ECONNRESET) on this machine's network** — safe to just retry `npm install` in place; partial installs don't corrupt the project.
- **`create-next-app` rejects directory names starting with `_`** (npm naming restriction) — use a plain name like `scaffold-tmp` when bootstrapping into a temp folder for a merge-into-existing-repo workflow.
- **The two "work sample" folders and the CV PDF are untracked, uncommitted local files** sitting in the repo working directory (not yet in git, not mentioned in `git status` output shown at session start beyond README.md). Worth deciding, before Stage 10, whether these raw source files get committed to the repo, gitignored, or live only in Blob storage post-upload.
- **Prisma installed at v7.9.1 — a major architecture change from the 5/6 patterns in training data. Do not assume old Prisma conventions.** Concretely, on this project:
  - `prisma init` no longer just writes `schema.prisma` + a `DATABASE_URL` line in `.env`. It also generates **`prisma.config.ts`** at repo root, which is what the **Prisma CLI** (`migrate`, `generate`, `studio`) reads for the datasource URL — `schema.prisma`'s `datasource` block now only has `provider = "postgresql"`, no `url = env(...)` line.
  - The default `generator client` provider is now **`prisma-client`** (not `prisma-client-js`), and it generates a TypeScript source tree into a custom `output` path (we used `src/generated/prisma`, gitignored automatically by the CLI) — not the old `node_modules/.prisma` + `@prisma/client` re-export pattern. Import the client from `@/generated/prisma/client`, not `@prisma/client` (that package now just provides shared runtime bits).
  - **The generated client requires an explicit driver adapter at runtime — it no longer reads `DATABASE_URL` implicitly.** For Postgres: `npm install @prisma/adapter-pg pg` (+ `@types/pg`), then `new PrismaClient({ adapter: new PrismaPg({ connectionString: process.env.DATABASE_URL }) })`. This is separate from `prisma.config.ts` (CLI-only) — the app's own runtime client needs the adapter wired manually. See `src/lib/prisma.ts`.
  - `prisma.config.ts` needs `dotenv` installed (`import "dotenv/config"` at its top) since it reads `process.env.DATABASE_URL` outside of Next.js's own env-loading.
  - Vitest does **not** auto-load `.env` like Next.js does — `vitest.config.ts` needs `import 'dotenv/config'` itself, or DB-touching tests silently fail to connect.
  - `prisma migrate dev` did not auto-run `prisma generate` reliably here — ran `npx prisma generate` explicitly afterward to produce `src/generated/prisma`.
- **Testing convention for this project:** DB-touching Vitest tests run against the real (free-tier, low-traffic) Neon dev database rather than a separate test DB — each test file uses a unique per-run prefix (e.g. `` `test-${Date.now()}` `` on slugs/emails) and cleans up its own rows in `afterAll`, relying on the schema's cascade deletes to sweep up children. Keep doing this for Stage 3+ tests rather than standing up test-DB infrastructure the project doesn't need yet.
- **`middleware.ts` is deprecated in Next.js 16 — renamed to `proxy.ts`.** Confirmed via `node_modules/next/dist/docs/.../file-conventions/middleware.md`, which redirects to `proxy.md`. Same request/response signature and `config.matcher` behavior, just: file renamed `middleware.ts` → `proxy.ts`, exported function renamed `middleware` → `proxy` (default or named export either works). A NextAuth v5 `auth(...)`-wrapped handler works fine as the default export of `proxy.ts` — the rename is purely about the file/export name Next.js looks for, not the function signature. Built this project with `src/proxy.ts` from the start rather than the deprecated name. `next build` output explicitly labels it `ƒ Proxy (Middleware)` when correctly detected.
- **NextAuth v5 (`next-auth@beta`, currently 5.0.0-beta.32) App Router wiring, confirmed against the installed package's own `.d.ts` files (not assumed from training data):**
  - `src/auth.ts`: `export const { handlers, signIn, signOut, auth } = NextAuth({ providers: [...] })`.
  - Route handler at `src/app/api/auth/[...nextauth]/route.ts` must destructure: `export const { GET, POST } = handlers;` — NOT `export { GET, POST } from '@/auth'` (that fails; `auth.ts` only exports `handlers`, `GET`/`POST` live inside it).
  - `src/proxy.ts`: `export default auth((req) => { ... req.auth ... })`, with `export const config = { matcher: [...] }` same as the old middleware convention.
  - Credentials provider's `authorize()` receives `credentials` (values from the form/POST body) and must return a `User`-shaped object (`{ id, email, ... }`) or `null` — never throw for "just wrong password," return `null` instead; NextAuth turns that into a `CredentialsSignin` error at the call site.
  - In a Server Action (e.g. the `/admin/login` form's `action`), a failed `signIn()` throws — catch it, check `error instanceof AuthError` (imported from `next-auth`, re-exported from `@auth/core/errors`), then call Next.js's own `redirect()` to show an error state; rethrow anything that isn't an `AuthError` (Next.js's internal redirect-on-success also throws internally and must propagate uncaught).
  - Verified the whole flow (correct login, wrong login, protected-route redirect, authenticated access) with `curl` against NextAuth's own endpoints directly — `GET /api/auth/csrf` for a token, `POST /api/auth/callback/credentials` (`csrfToken`, `email`, `password`, `redirect=false`, `json=true`) to sign in, `GET /api/auth/session` to confirm session state — rather than needing a browser. Useful pattern for testing future auth-gated stages without browser automation.
- **Resend free tier blocks sending to anyone but the account owner's own email, until a domain is verified.** Confirmed live: `resend.emails.send({ from: 'onboarding@resend.dev', to: 'shruti2004shahu@gmail.com', ... })` returns a 403 (`validation_error`: "You can only send testing emails to your own email address (`srivastavaaryan97497@gmail.com`)..."). The Resend account was signed up with Aryan's email, not Shruti's — so any transactional email to Shruti (password reset, contact form notifications in Stage 8) will silently fail to deliver until either: (a) a real domain is verified in Resend and used as the `from` address (which also lifts the recipient restriction), or (b) Shruti's own email becomes the Resend account owner. **Not a code bug** — `createPasswordResetToken`/the whole reset flow works correctly regardless; only actual delivery is blocked. Flagged as an open decision, not silently worked around. This will also block Stage 8 (contact form) the same way — worth resolving before then, e.g. by verifying a domain once one exists for the site.
- **Server Actions can be tested over plain HTTP without a browser**, since a `<form action={serverActionFn}>` degrades to a normal multipart/form-data POST to the same URL: fetch the page, extract the hidden `$ACTION_ID_<hash>` field name from the rendered HTML, then `curl -F "$ACTION_ID_<hash>=" -F "otherField=value" -X POST <same-url>`. Confirmed working for both the forgot-password and reset-password forms this stage. Same technique will apply to Stages 5/6/8's admin forms.
- Directly testing library functions (bypassing the Next.js page/action layer) requires `import 'dotenv/config'` at the top of the script and running via `npx tsx <file>.ts` **from the project root** with a relative import (e.g. `./src/lib/prisma`) — cross-directory absolute imports from the OS temp scratchpad didn't resolve cleanly with tsx's module resolution; simplest fix is to write the one-off script inside the repo root, run it, then delete it.
- **Vitest's default 5s test timeout is too tight for tests that make multiple real round-trips to the Neon DB plus bcrypt hashing** — hit one transient timeout on a test that had passed moments earlier. Bumped `testTimeout: 15000` globally in `vitest.config.ts` rather than per-test, since this project's whole testing convention (see above) is hitting the real free-tier DB, not mocks — expect this to matter more as tests accumulate in Stages 5–9.
- **A page with no dynamic API usage of its own gets statically prerendered at build time by default, even under an authenticated `/admin/*` proxy.** `/admin/categories/page.tsx` only calls plain async DB functions (no `auth()`, no `searchParams`) — Next.js happily prerendered it (`○` in the build output) and would have served build-time-frozen category data to every visitor forever. `auth()`-calling pages (`/admin`) and pages reading `searchParams` (`/admin/login`, the reset flow) were fine, since those are themselves dynamic APIs that opt a page out of static rendering automatically. Fix: `export const dynamic = 'force-dynamic'` (confirmed current/correct via `node_modules/next/dist/docs/.../caching-without-cache-components.md` — this project isn't opted into Next 16's new `cacheComponents` flag, so the classic route-segment-config API still applies). **Checklist item for every future admin page:** if it doesn't call `auth()` or read `searchParams`/`params`/cookies itself, it needs this explicitly, or it'll silently go stale.
- **Prisma's `update()` `where` clause accepts extra non-unique filter fields alongside the unique one** (e.g. `{ id, parentId }`, not just `{ id }`) — confirmed via the generated `CategoryWhereUniqueInput` type (`Prisma.AtLeast<{...}, "id" | "slug">`). Useful as a cheap extra safety check on mutations (e.g. `reorderCategories` scoping the update to the expected parent) without a separate read-then-write.
- **Running `npm run build` immediately before `npm run dev` in the same session can leave `.next` in a state where API routes 404** (hit this with `/api/auth/*` right after a Stage 5 production build) — both commands share the `.next` directory and a stale/mixed build+dev cache broke route resolution. Fix: `rm -rf .next` before starting `dev` if you've just run `build`. Worth doing as a matter of course when switching between the two rather than debugging the 404 each time.
- **`@vercel/blob`'s server-side `put()` (used for cover/gallery image uploads) is capped at a 4.5MB request body on Vercel-hosted deployments** — fine for real photos (our reviewed samples are all under 200KB), but would break for large PDFs. Not a local-dev limit (no cap running `next dev`), and doesn't apply to a Node script calling `put()` directly outside an HTTP request (e.g. a future seed script uploading the 18MB Creative Portfolio PDF wouldn't hit this). If project doc/link uploads ever need to go through the web form for files that size, switch to Blob's **client upload** flow instead (`@vercel/blob/client` + a signed-token route handler) — deliberately not built now since it's outside Stage 6's actual scope (images only).
- **Tiptap v3 (`@tiptap/react` 3.29.2) requires `immediatelyRender: false` in `useEditor()` for Next.js SSR** (confirmed via the installed package's own overloaded type signatures — the `immediatelyRender: false` variant returns `Editor | null`, the default variant `Editor`) — omitting it causes a hydration mismatch since the editor can't render server-side. The editor's HTML is bridged into the surrounding server-action form via a controlled hidden `<input type="hidden" name="description" value={html}>` that updates `onUpdate`; the server action reads it via plain `formData.get('description')` same as any other field, no special handling needed there. `StarterKit` does NOT include the Link extension by default (separate `@tiptap/extension-link` package) — left out of the toolbar for now since links live in the separate `links[]` field already.
- **`<form action={someServerActionFunction}>` must NOT also specify `encType` (or `method`) manually** — React sets these automatically for function actions (detecting file inputs itself to pick multipart) and throws a console warning ("will get overridden") if you set them yourself. Had `encType="multipart/form-data"` hardcoded in `ProjectForm.tsx`; removed it. File uploads still worked correctly without it.
- **`ProjectForm` uses a fixed number of link label/url slots (`LINK_SLOTS = 6` in `src/lib/projects.ts`) rather than a dynamically-growable list** — deliberate choice to keep every admin form pure server-actions/no-client-JS (consistent with the whole project so far), since our real seed content never needs more than 2 links per project. Blank slots (empty label or url) are silently dropped on save (`parseProjectFields`/`createProject`/`updateProject` all filter them). Revisit if a real project ever needs more than 6 links, or when the design pass adds client-side interactivity anyway.
- **Deleting a project does not delete its Blob-stored cover/gallery images** — they become orphaned in Blob storage (harmless on the free tier at our scale, but real technical debt). `deleteCategory`'s cascade mode has the same gap for any projects it sweeps up. Not fixed now — outside Stage 6's stated scope — but worth a cleanup pass (call `del()` from `@vercel/blob` for each image) before this matters at any real scale.
- **A specific curl quoting quirk in this sandboxed Bash tool: a `-F "field=<html with angle brackets>"` value (e.g. testing the Tiptap-produced `<p>...<strong>...</strong></p>` description) intermittently breaks the request with `curl: (26) Failed to open/read local data from file/application`**, even though the value is properly double-quoted and valid shell syntax. Isolated by bisecting field-by-field — reproducible specifically when the value contains literal `<`/`>` characters. **Workaround:** write the value to a file and use curl's own `-F "field=<path/to/file"` (read-value-from-file) syntax instead of inlining HTML/angle-bracket content directly in the command string. Also learned: this environment's working directory does NOT reliably persist relative paths across every Bash tool call the way plain bash normally would (`cd /tmp` succeeded once then a later call was back at the project root) — prefer absolute paths for any file referenced across multiple tool calls, and note that native Windows Python (not MSYS-aware) can't resolve MSYS-style `/tmp/...` paths that `bash`/`grep`/`cat` handle fine — use `grep`/`cat` (MSYS-native) instead of spinning up Python for quick text extraction from HTML responses when absolute Unix-style paths are in play.
- **Internal navigation links must use `next/link`'s `<Link>`, not plain `<a href="...">`** — ESLint's `@next/next/no-html-link-for-pages` flags this (at least reliably for statically-resolvable paths like literal `href="/"`; template-literal hrefs like `` `/category/${slug}` `` weren't flagged by the linter but were fixed proactively anyway for consistency). External URLs (e.g. a Blob-hosted resume PDF) correctly stay as plain `<a>` — `Link` is only for in-app routes.
- **Category `slug` is globally unique (not scoped per-parent) in the schema, so public category URLs are single-segment (`/category/[slug]`)**, not a full hierarchical path like `/category/marketing/video-scripts/instagram`. Breadcrumbs are still computed and displayed correctly by walking the `parentId` chain server-side (`getCategoryBreadcrumbs`) — this is a URL-shape simplification, not a navigation limitation. Revisit only if SEO/URL-aesthetics ever calls for full nested paths.
- **Testing the public pages didn't require re-driving the admin HTML forms through curl** (unlike Stages 4–6) — since Stage 7 is about verifying the *read*/rendering side and the admin *write* side was already proven in Stages 5–6, test data was seeded by calling `createCategory`/`createProject`/`prisma.siteContent.upsert` directly from a one-off `tsx` script, then the public pages were checked with plain `curl` GETs. Faster and avoids the curl/shell quirks noted above (no HTML content needed in a `-F` value this time). Good pattern to reuse: use the admin-form-through-curl approach only when specifically testing the admin mutation UI itself; use direct lib calls to seed data when testing something else (like public rendering) that merely *depends on* data existing.
- **`SiteContent` has no admin UI to populate it until Stage 9** — Stage 7's public pages (Home, Contact) must and do handle a completely absent singleton row gracefully (rendered "coming soon" fallback text), since that's the real state of the live dev DB right now. Verified both the empty-state and populated-state rendering, then deleted the test `SiteContent` row afterward to leave the DB in its real (empty) current state — same one-shot-singleton cleanup care as `siteContent.test.ts`.

Reproduced reliably via Playwright by simulating the real flow (Home → click into Contact → fill and submit the form → land on `/contact?sent=1`) and comparing `document.body.scrollHeight` to `.site-shell`'s actual rendered height — a fresh `page.goto()` per page never reproduced it (each fresh load remeasures correctly on mount), only a sequence of client-side navigations within one session did. **Fix, two parts:** (1) exclude the SVG's own footprint from each measurement — set its `height` attribute to `0` immediately before reading `document.documentElement.scrollHeight`, then restore it, breaking the self-reference; (2) add a `MutationObserver` on `document.body` (`childList`+`subtree`, rAF-throttled) alongside the existing `ResizeObserver`, since same-pathname navigations (e.g. `/contact` → `/contact?sent=1`, which only adds a success banner) don't reliably fire a body-*size* change event the `ResizeObserver` would catch on its own. **Lesson: any component that measures `document.body`/`documentElement` to size itself, and then renders something that itself occupies space in that same document, has a latent self-referential feedback-loop risk — especially in a persistent layout component that survives client-side route changes** (a fresh mount per page, which this project's `(site)/layout.tsx` does NOT do, would have masked this entirely).

Kept as a small standalone component rather than converting the whole Contact page to a client component, preserving the established plain-HTML-form-plus-Server-Action pattern everywhere else on the page.
- **`node_modules` corruption recurred a third time** (all 8 vitest files failing with the same `Cannot read properties of undefined (reading 'config')`, "Test Files 8 failed (8)", full-suite-only) even with no leftover `node_modules/playwright` directory this time — same fix as before (`rm -rf node_modules && npm install`) resolved it in one pass (49/49 passing after). **Lesson reinforced: treat any full-suite-only, single-error-message-across-every-file test failure as a `node_modules` state problem first**, and re-verify with a clean reinstall before investigating the code — this has now happened 3 times in this session with no code-level cause found any of the times.
- **Reworked the Services section into a responsive bento grid** (asymmetric cell spans — one large featured cell, one tall cell, several regular ones) after the user shared a reference mockup. The mockup's cards also had per-service description copy and a "MOST REQUESTED" badge — deliberately **left both out** since neither was previously-approved real content (the original Locked decision only specified the 6 service names, no descriptions, and "most requested" would be an unverifiable factual claim about Shruti's business) — implemented the mockup's *layout pattern* only, keeping the existing approved names/icons. Responsive strategy: complexity scales up with viewport width rather than trying to force the intricate desktop bento shape into a narrow screen — mobile is a plain single column with no spans at all, tablet is a simple 2-column pairing (with the wide "hero" cards still full-width), and the full asymmetric bento (`grid-cols-4` + `row-span`/`col-span` + `grid-flow-dense`) only applies at `lg:`.
